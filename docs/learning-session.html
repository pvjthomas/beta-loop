Zeon Systems

Writing robot lab automation protocols as code — from a drug screening hackathon to a mental model you can take to any lab.

🧬 Hook: TEM-1 β-lactamase inhibitor screen 📦 Project: beta-loop / mastermix 🎯 Goal: Understand the whole system, zero to running protocol

What is Zeon?

Zeon is a platform for writing robot lab automation protocols as code. It replaces drag-and-drop scheduling software with a programmable stack — skills in Python, workflows in JSON, world models in YAML, and optionally a custom React run-setup UI.

💡 Analogy
If Hamilton / TADM is Excel, Zeon is Python. You trade the drag-and-drop interface for full programmability, composition, and reproducibility.
🗂️

Plain text files

Everything is a file in a directory. Python, JSON, YAML. Version-controlled by Zeon's own VCS (zeon sync).

🌐

Web UI as operator terminal

Workflows run only from the web UI — never from the CLI. The Canvas form is the "start run" interface.

⚓

Anchors, not coordinates

Skills never hard-code robot positions. They reference named poses on objects. If equipment moves, the code doesn't change.

🔄

Calibration stack

5 layers from nominal bench layout down to per-well pipetting offsets. Each layer answers a different question.

The 5-Layer State Stack

The most important mental model. Each layer answers a different question. Understanding this explains nearly every design decision — and every hackathon failure mode.

1. world_state.json

Nominal bench layout — what objects exist and where they approximately are.

xyz + quaternion poses · collide_in_planner flags · joint initial states
↓
2. object_model.yaml + URDF

Where are the grab points, wells, and joints on this object type? Geometry and interaction points for each object type.

links · joints · collision shapes · named anchors · well coordinates
↓
3. live_state.yaml

What calibration offsets and runtime state apply to this specific instance? Mutable calibration on top of the nominal model — changes during a run.

TCP offsets · per-well XY deltas · tip counters · in_hand state
↓
4. Skills (Python)

Robot behavior. Resolves anchors at runtime, reads/writes live_state.

robotic_code.py · load_object_anchor() · move_arm() · set_gripper()
↓
5. Workflows (JSON)

Sequence and logic. Binds skill parameters to run inputs.

nodes · on_success / on_failure edges · {"$input": name} binding
Key insight
Skills never contain hard-coded coordinates. They call load_object_anchor(object_id, anchor_name), which resolves through all layers at runtime — including any AprilTag relocalization that may have updated the object's pose.

⚠️ FixedMount ≠ immovable
FixedMount describes how the pose is stored in the file. Skills can pick up objects; AprilTag localization can update runtime poses. The word "fixed" only means "not a joint."

Skills — Robot Actions as Python Functions

# skills/cfps_dispense_mastermix/robotic_code.py
def cfps_dispense_mastermix(
    pipette:        SkillObject,    # required — no default
    tipbox:         SkillObject,
    reagent_block:  SkillObject,
    reaction_plate: SkillObject,
    mm_anchor:      str,            # which anchor to aspirate from
    wells:          list,           # ["A1", "A2", ...]
    rxn_volume:     float,
    num_reactions:  int,
    speed:          int = 80,      # optional — has default
) -> dict:
    ...
    return {"success": True}       # or raise — NEVER return {"success": False}
What this skill does
This skill dispenses a master-mix reagent from a cold block tube into reaction wells on a plate. It doesn't call move_arm() directly; it composes three lower-level skills (epipette_aspirate, epipette_dispense, epipette_eject), showing that skills can be built from smaller skills.

The arguments split into two groups: physical objects (which pipette, tipbox, source block, destination plate) and protocol parameters (which hole to aspirate from, which wells to fill, volume per well, how many reactions to run).
📐 The function signature IS the schema
The Zeon app reads the function signature and auto-generates an input form from it — rxn_volume: float becomes a number field, SkillObject becomes a dropdown of world objects, and parameters without defaults are required. Default values are set in the workflow JSON (defaultValue on each input). A canvas (optional React UI) can replace the auto-generated form with a richer setup experience.

Two tip management strategies

🔴 Pattern A — Fresh tip per stroke

Safe Expensive

New tip for every aspirate-dispense cycle. No cross-contamination possible. Used in the original hackathon code (cfps_dispense_mastermix).

🟢 Pattern B — Batch aspirate

Efficient Homogeneous only

One aspirate for N wells, dispense each, eject once. Used in the improved version (batched_dispense_mastermix). Safe only when the liquid is the same across all wells.

Rules every skill must follow

  • Enter and exit through transition poses (named joint-space stow positions). Skipping causes IK failures when skills are composed.
  • Failure is raise, not return {"success": False}. Returning false does not stop the workflow.
  • Snap after every pick — call snap_plate_into_gripper() to assert the canonical grip relationship in the simulator.

Canvas — The Run Setup UI

When a workflow declares "canvas_ui": {"kind": "react", "source_ref": "canvas/cfps_mastermix_screen.tsx"}, the web UI renders a custom React form before starting the run.

Sandboxed iframe
The canvas is isolated. Only import React from "react" is allowed. No network access, no filesystem. Communication is through zeon.* globals injected by the host.

Hackathon Observations → Architecture Lessons

Four things that went wrong — each exposes a real architectural constraint.

1
Tip stuck on discard — pipette stopped
live_state.yaml · set_gripper() write-only · physical state desync
▶
"Tip got stuck when being discarded; pipette stopped moving."

What happened: Tip eject failed. The arm halted rather than recovering.

Why the architecture can't auto-recover: set_gripper() is write-only — there is no read-back. The system cannot confirm whether the tip released. attach_next_tip() may have already incremented the tip counter before the physical eject was confirmed, so the world model and physical reality diverged.

Design constraint
Pressure monitoring (Hamilton TADM-style) can catch aspiration failures and pickup failures — but not eject failures. Detecting a stuck tip requires either force sensing or a camera with line-of-sight to the tip chute.

General lesson: This is the central difficulty of physical automation. The system's model of state and the physical world can diverge at any step where there is no sensor read-back to confirm the action succeeded.

2
Simulation slow, no fast-forward, pause corrupted state
workflow executor · viser.studio viewer (not physics sim) · physical state checkpointing
▶
"Simulation takes too long, cannot fast forward, cannot restart from the middle; pausing the experiment messed up something."

What "simulation" means here: The 3D view is viser.studio — a Python-native browser-rendered scene viewer (WebGL/Three.js). It shows what the robot thinks the world looks like. It is not a physics simulator. It doesn't model fluid dynamics, deformable bodies, or contact forces.

Why there's no fast-forward: The workflow executor sequences real-time skill calls. Even in sim mode, skills run at real-robot speed because the timing matters (settle times, gripper actuation, IK computation).

Why pause corrupts state: Pausing mid-skill leaves the arm at an unknown intermediate pose, live_state.yaml possibly not flushed, and async operations in flight. There is no checkpoint mechanism for physical state.

Fundamental constraint
Physical automation cannot "seek" to an arbitrary past state — unlike pure software. Design experiments as sequences of independently resumable skills with explicit checkpoints.
3
Vibe-coded movement — tip waste, unnecessary home-returns
skill authoring · tip management · path sequencing
▶
"Vibe coded movement not optimal (not reusing tips, return to position before moving to the next spot)."

Two inefficiencies:

  1. Not reusing tips — acquiring a new tip for operations where the same tip could have been used. Wastes tips, adds discard overhead (see Observation 1).
  2. Home-return between every move — swinging to stow before every target instead of moving directly. Unnecessary travel time on every step.

Why the planner doesn't fix this: The motion planner finds collision-free paths between two poses. It does not optimize tip reuse or minimize travel across a multi-step protocol. These are authoring decisions, not planner constraints.

The fix for tip reuse: batched_dispense_mastermix — one aspirate for N wells, dispensing continuously, ejecting once. This is the version that actually ran in the final hackathon demo.

4
Wireless cube button pusher device
workcell integration · auxiliary actuators · instrument APIs
▶
"Wireless cube ish button pusher."

What it is: A small wireless actuator for pressing physical buttons on lab instruments that lack a software API — e.g., a plate reader "start" button or sealer activation.

Why it exists: Lab instruments often have physical controls that predate software integration. Pressing a small button with the robotic arm is awkward and collision-risky. A purpose-built BLE actuator fills the gap cheaply.

Integration pattern: Such a device is typically wrapped as a workflow step — similar to how the SiLA2 driver wraps the PreciseFlex400 arm as a callable device. The workflow calls it like any other skill node; the implementation handles the BLE connection.

Going to a New Lab — Zero to Running Workflow

Bootstrap the project

zeon new project my_lab_project
cd my_lab_project

Pulls a scaffold from the Zeon server. Not git init — this is zeon new, which seeds from the server with the directory structure and CLAUDE.md authoring guide.

Import object models from the shared mesh database

zeon new object plate_reader
zeon new object wellplate_96_flatbottom
# ... for each piece of equipment

Each import creates objects/<type>/ with the URDF, geometry, and anchor definitions. If a type doesn't exist in the shared database, it needs 3D scanning or modeling — this is the hard part.

Build world_state.json

Hand-author or use the World Builder UI. Place objects with approximate poses — exact accuracy isn't required at this stage. AprilTag localization will refine poses at runtime.

Physical AprilTag stickers must be placed on each piece of equipment matching the tag anchors in the object model.

Initialize live_state.yaml

epipette_10ul:
  tcp_offset: [0.0, 0.0, 0.0]  # will be calibrated
  in_hand: false
tipbox_10ul_1:
  tip_index: 0
  active: true

Calibrate (the time-consuming part)

  • TCP calibration — touch a reference point; solve for pipette TCP offset → live_state.yaml
  • Per-tip attachment calibration — record XY offset for each tip position → live_state.yaml
  • Per-well dispensing calibration — aspirate and dispense; inspect landing vs. nominal → live_state.yaml
  • AprilTag verification — move an object, run localization, confirm load_object_anchor shifts by the same amount

Author anchor-driven skills

Always reference load_object_anchor(), never literal coordinates. The skill should work if the equipment is relocated.

Wire a workflow, push, run

zeon sync -m "initial world setup"

Then: web UI → select project → select workflow → fill Canvas form → start run.

Teaching the Robot New Movements

To teach a robot a new movement, you need to know where to move (coordinates) and how to move (forces, speeds, approach strategies, failure handling).

Capturing coordinates — jog, record, promote

  1. Jog the arm to the desired position — on real hardware via the Zeon UI, or in the World Builder's 3D view for simulation.
  2. Record the pose — call get_arm_pose("right_arm"), which returns [x, y, z, roll, pitch, yaw] in world-frame coordinates, or read joint angles from the Dev Tools panel.
  3. Prototype — paste those coordinates into your skill code and test in simulation using the Skills Editor (which runs a single skill against a loaded world). Movements can fail: IK can't reach the target, the arm collides with something, or the coordinates have drifted from what you intended. Iterate until the movement works in sim, then verify on real hardware at reduced speed with someone at the stop control.
  4. Promote to an anchor — add the validated pose as a named anchor in the relevant object's object_model.yaml (the object the movement is relative to — e.g., the grasp point on a pipette, or a well position on a plate). Skills then use load_object_anchor() instead of hard-coded numbers, and the position survives if the object moves on the bench.
Promoting requires a coordinate transform
get_arm_pose() returns world-frame coordinates, but anchors in object_model.yaml are relative to the object's own frame (link_T_anchor). To convert: 
anchor_local = inverse(object_world_pose) ∘ arm_world_pose

Example: teaching a new process with the tacit-teacher

Beyond coordinates, a new movement needs design knowledge — forces, speeds, failure handling, verification criteria. The tacit-teacher process captures these by combining video analysis with expert interviews, producing a provenance-tracked parameter set. Coordinates still come from jogging (above).

Step 1: Video analysis (VLM-driven)

Record the human expert performing the task. Run the footage through a vision-language model (e.g., Gemini) which extracts what it can observe: timing, phases, approximate angles, observable failure modes. Critically, it also flags what it cannot determine — forces, verification criteria, intent. These gaps become the interview agenda.

Step 2: Structured interview

Interview the expert, using the VLM's gaps as questions. Six categories:

📐 Geometry
"Where do you reach? Which direction do you approach from? Is there a prepose?"
💪 Force
"How hard do you grip? What does success feel like vs. failure?"
⏱️ Speed / timing
"Which parts are fast vs slow? Any pauses? Does speed matter?"
✅ Verification
"How do you check after each step that it worked?"
⚠️ Failure / recovery
"What goes wrong most often? How do you recover? When do you stop?"
🔄 Variation
"Does it differ by batch, brand, temperature? What stays the same?"

Step 3: Extracted YAML

The video analysis and interview produce a structured YAML file that can inform the skill author. Each parameter captures a constraint (geometry, force, timing, failure handling) and cites which interview question or video timestamp it came from. Real examples from the peel_seal session:

# geometry — video estimated 45-90°, expert corrected it
# → skill author computes the orientation for move_arm() that
#   achieves a 45° pull relative to the plate surface
peel_angle_deg:
  value: 45
  source: [Q3, V1, V2, V3]
  method: stated
  superseded:
    was: {value_range: [45, 90], method: vlm_estimate}
    corrected_by: Q3

# force — no number, just a behavioral threshold
# → set_gripper() to minimum width; only risk is too loose
grip_mat:
  value: maximum
  source: Q2
  method: stated

# timing — measured from video frame timestamps
# → calibrate move_arm() speed so the full peel takes ~15s
peel_duration_s:
  observed_range: [13, 19]
  per_clip: {V3: 13, V4: 17, V1: 18, V2: 19}
  source: [V1, V2, V3, V4]
  method: measured

# failure — recovery rules from the interview
# → try/except in the skill: retry once if nothing spilled
mat_stays_sealed:
  recovery: retry_peel
  max_retries: 1
  retry_precondition: "nothing spilled and plate has not moved"
  source: [Q5, V7@00:15]
  method: stated

The YAML captures what the expert knows; the skill author decides how to translate that into skill code (angle → orientation, duration → speed, recovery rule → try/except).

Step 4: Coordinates still come from jogging

The tacit-teacher process produces design parameters — angles, forces, speeds, failure modes, verification criteria. The actual robot coordinates for the skill are still captured by jogging the arm (the process described above).

Summary — Q&A

What is a Zeon project?

A plain directory of Python skills, JSON workflows, YAML worlds, and optional React canvas — versioned by zeon sync (like Git but with binary asset support).

How does the robot know where to go?

Anchors — named poses defined in the object model YAML, relative to the object. Resolved at runtime by load_object_anchor(), which composes the object's world pose (layer 1) with the anchor's local offset (layer 2) and any calibration deltas (layer 3). If the object moves, the anchor moves with it.

What's live_state.yaml?

Per-instance calibration and runtime state (layer 3): TCP offsets, per-well XY deltas, tip counters, in_hand state. Keyed by object UUID so two instances of the same type can have different calibration. Skills read/write it via get_world_state() / set_world_state().

Why did the tip stuck issue break state?

set_gripper() is write-only. The system cannot detect a stuck tip. The tip counter may have incremented before the physical eject was confirmed, leaving the model and reality diverged.

Why can't you pause mid-experiment?

Physical state — arm position, tip attachment, liquid volumes — has no checkpoint mechanism. Pausing mid-skill leaves state inconsistent with no safe way to resume.

How do you set up Zeon in a new lab?

Bootstrap project → import object models from shared mesh DB → build world_state.json (approximate OK) → initialize and calibrate live_state.yaml → author anchor-driven skills → push and run from web UI.

How do you teach the robot a new movement?

For coordinates: jog the arm (Zeon UI or World Builder), record with get_arm_pose(), prototype in code, then promote to object model anchors via a coordinate transform. For design knowledge (forces, speeds, failure handling): the tacit-teacher process is one approach — video analysis + expert interview → structured YAML that informs the skill author.
